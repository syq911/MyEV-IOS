- **元组没有 keypath**：`ForEach(Array(x.enumerated()), id: \.offset)` 编译不过；
  正解是让类型自己给 `Identifiable` 的 `id`。
- **`Section("标题") { … } header:/footer:` 编译不过**（便捷初始化器不能再接标签）。
  已固化成 `check_swift_syntax.py` 的新规则并双向验证。
- **我自己写的测试红了 3 条**：参数表把 `isRightToLeft/isLeading` 写反、
  单调性断言从宽度 0 起步（0 走兜底值 60，比下限 44 大）、
  把「取消」当成需要确认的操作（策略里明确不确认）。
  → 教训：**断言的期望值必须能从规则本身推导出来**，凭印象填表就会红。
- **`settle` 等 `isBusy` 是错的**：`isBusy` 的语义是「现在没事干」（给进度条用的），
  不是「该干的事都干完了」。改为 `settle(expecting: n)` 等**结果**，
  并先断言 `failureMessage == nil`（否则「少了一页」既可能是没跑完也可能是真失败）。
- **GitHub push 返回 500**（`! [remote rejected] main -> main (Internal Server Error)`）：
  同一批对象推到**新分支**成功、随后更新 main 也成功。以后遇到就
  「先推临时分支把对象送上去，再推 main」，不必怀疑自己的仓库。

## 根因找到了（0.0.3）：`__objc_protorefs` 被放进只读段

**Xcode 26 的链接器默认把 `__objc_protorefs` 放进只读的 `__DATA_CONST`**
（Xcode 16 及更早放在可写的 `__DATA`）。拆开 0.0.1 的 IPA 实证：

```
segment=__DATA_CONST  section=__objc_protorefs
segment=__DATA        section=__objc_const / __objc_selrefs / __objc_data
LC_BUILD_VERSION  minOS=18.0.0  SDK=26.5.0
[LOAD] /usr/lib/libobjc.A.dylib
```

dyld 在 fixup 完成后把 `__DATA_CONST` 标记为只读，随后 `map_images_nolock`
做 protocol fixup 时仍要写 `__objc_protorefs` → **`EXC_BAD_ACCESS (SIGBUS)`，
发生在 `main()` 之前**。一条机制解释了全部反常现象：启动即闪退（死在业务代码
之前）、多半没有正常 crash report、模拟器与 CI 全绿（模拟器对 `__DATA_CONST`
保护宽松且不校验签名；997 个用例以 App 为宿主跑 = 已证明模拟器上能启动）、
只有 iOS 18 真机中招（iOS 26 的运行时行为已与链接器对齐）。

**修复**：App target 的 Debug / Release 各加 **`-Wl,-no_data_const`**。
**验证**：`otool -l <二进制> | grep -A2 __objc_protorefs` —— `segname` 必须是
`__DATA`。已把这条固化成 CI 的一步（回到 `__DATA_CONST` 直接失败）。

**方法论沉淀（这次最关键的一条）**：这类问题**本地完全看不见**——不是编译
错误、不在测试覆盖里、模拟器永远不复现。**手里有产物时，直接拆二进制看结构
（Mach-O 的 segment / section），比读代码猜有效得多。** Python 用 `struct`
解 Mach-O 就够了，不需要 macOS：读 header → 遍历 load commands →
`LC_SEGMENT_64` 里取每个 section 的 `segname` / `sectname`。

版本线：0.0.1（首个测试版，真机闪退）→ 0.0.2（诊断：BootTrace + 文案表降级，
仍闪退）→ **0.0.3（修复）**。
